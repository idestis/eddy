# Performance after ADR-0006 P1

These are the same load generator and benchmarks as [baseline.md](baseline.md), run on the
same machine (Apple M2 Max, 12 cores, Go 1.27.1) after the P1 changes of
[ADR-0006](../adr/0006-progressive-loading.md).

## What P1 changed

- **Compression:**
  - gzip on `GET /api/v1/…`: level 5 for bodies of 1 KiB or more, level 1 with a flush per event for SSE.
  - permessage-deflate with context takeover on the agent and peer WebSockets. The read limit still counts decompressed bytes.
- **Validators:** weak ETags and `If-None-Match` → 304 on `/clusters`, `/resources`, `/kinds`, `/attention` and `/threads`.
- **Authorizer:**
  - It asks the cluster-scope question once per kind before any per-namespace one.
  - The SAR cache holds 250k answers.
  - Agent replies are no longer throttled by the 200 frames/s limit, which starved pongs.
- **Counts:**
  - Kept incrementally per tuple, with per-kind totals: O(kinds) for a user who may list a kind cluster-wide.
  - `ClusterInfo.kinds` gives per-kind counts for the sidebar.
- **New endpoints:** `GET /api/v1/search` (a Go port of `fuzzy.ts` over the hub's views) and `GET /api/v1/attention`.
- **Snapshots** are staged until their last part (`Snapshot.parts`, `Delta.part`).
- **Disconnected clusters** keep a stale view.

## Verdict on the measurement gate

P1 meets the budgets **for a single user with cluster-wide read access**. It fixes the
baseline's collapse: agents stay connected, SAR drops 138×, and transfers shrink 10–5,000×.
It does **not** meet them in two cases, both at the target scale:

1. **SSE fan-out to many users.** Every stream receives every delta of every cluster.
   That is about 630 events/s per user, and 50 such users saturate a 12-core hub. Every
   other request then waits: fleet p50 is 520 ms and the palette p50 is 970 ms. This is
   exactly what **P2's SSE `watch=` (at most 5 clusters) plus `counts` events** removes.
   **P2 is needed.**
2. **Namespace-scoped users.** Without cluster-wide list, a user still needs one SAR per
   (kind, namespace) per cluster: about 222k per fleet view at 100 clusters × 200
   namespaces. One such user nearly fills the 250k cache, so a few of them thrash it for
   everyone, admins included. The fleet page takes 7–10 s and the palette 21–29 s.
   - Neither P2 nor P3 as written fixes this. The ADR's "~20 checks per user per cluster"
     assumes cluster-wide read.
   - A separate, small, additive change would: answer access per namespace from one
     `SelfSubjectRulesReview` per (user, namespace), impersonated by the agent. That covers
     every kind of a namespace in one call, 200 instead of 3,400 per cluster. It needs a
     new agent op and an owner decision; see the report.
3. **Memory** stays about 2.2 GiB per replica: every replica holds full summaries of every
   cluster. Only **P3** (T2 on the agent) brings it toward 0.8 GB. P1 did not aim to change
   it. Whether P3 is needed depends on the owner's memory budget per replica, which the ADR
   states only as the "≤ 0.8 GB" target.

`-role` makes every user `admin`, `team` or `mixed`; without it the mix is 20 % admin,
50 % team and 30 % mixed. The default 50-user mix at 100 × 15k does not finish in
reasonable time on P1: it is the namespace-scoped SAR storm of case 2.

## P1.1 rules review

P1 left namespace-scoped users at about 222k SubjectAccessReviews per fleet view, and a few
of them thrashed the shared 250k-answer SAR cache for everyone. P1.1 adds an agent op,
`rules`. The agent creates one `SelfSubjectRulesReview` per (user, namespace), **as the
impersonated user**, at most 50 namespaces per request. The hub then answers namespaced
`get`/`list`/`watch` checks from those rules.

- **Fallback:** the hub uses a SubjectAccessReview whenever the rules cannot give an exact
  answer: the review is incomplete, has an evaluation error, failed or was truncated; or
  the baseline (`eddy:rules-baseline`, which covers what `system:authenticated` adds
  through impersonation) allows the same check.
- **Cluster-scope checks** (one per kind per cluster) stay SubjectAccessReviews.
- **Cache:** rules reviews are cached for 45 s, in their own cache. It holds up to 1M
  entries, about 150 B each, and identical rule sets are stored once. SAR answers are no
  longer spent on per-namespace checks that rules can answer.

Same machine and data as above (100 clusters × 15k, 1.5M rows, 200 namespaces per cluster).
"Before" is the same build with `-no-rules` / `-loadgen.norules`, so agents answer only SARs,
as in P1.

**20 users in the default mix** (20 % admin, 50 % team, 30 % mixed) for 60 s. P1 could not
finish this mix.
- **Requests:** fleet p50 552 ms / p95 1.3 s; fleet palette p50 708 ms; list p50 99 ms. No
  errors, 0 reconnects.
- **Access:** about 1,700 SAR checks and 19,900 rules reviews per namespace-scoped user per
  minute.
- **CPU:** the hub ran at 899 % of a core, about 27 % of a core per unscoped SSE stream. This
  is P1's case 1 (SSE fan-out), which P2's `watch=` removes. It is no longer the access
  checks.
- **Memory:** live heap 2.54 GiB, rules cache included.

### Verdict

Case 2 of the P1 verdict is fixed. Namespace-scoped users now cost about one SAR per kind
per cluster plus one rules review per namespace. Their warm fleet page is 17 ms in the hub
and 30–80 ms end to end, and they no longer evict the answers of cluster-wide users. The
rules cache is bounded separately: 1M entries holds 50 namespace-scoped users at 100 × 200
namespaces, about 145 MiB when full.
