# Performance after ADR-0006 P2 (scoped live updates)

Same load generator and machine as [p1.md](p1.md) (Apple M2 Max, 12 cores, Go 1.27.1):
100 clusters × 15,000 resources (1.5M rows), churn 5 changes/s/cluster, 50 users with
cluster-wide read (`-role admin`), 60 s of browsing. "Before" is the same build with the
unscoped stream (`-watch -1`, no `?watch=`), which is exactly the P1 behaviour; "after" is
every user watching one cluster (`-watch 1`), what the web UI does on a cluster page.

## What P2 (backend, live updates) changed

- `GET /api/v1/stream?watch=a,b` (at most 5): `change` events only for watched clusters.
  Every cluster gets `counts` (debounced to 1/s per cluster, only on change, from the P1
  incremental per-kind counts) and `attention` (rows entering or leaving the needs-attention
  set, plus findings), filtered per user with the same list rule.
- Scoped streams receive `clusters` only on connect and on connection or cluster-set
  changes, no longer on every count change (each one was 420 KiB raw for 100 clusters).
- `GET /api/v1/search` takes `kind=`.

## SSE fan-out (50 streams open, churn on, no requests)

| | Before (unscoped) | After (`watch` 1 cluster) | Change |
|---|---|---|---|
| Events/s per user | 628 (627 `change`) | 37 (6.3 `change` · 14.4 `counts` · 16 `attention`) | 17× fewer |
| Wire bytes/s per user (gzip) | 128 KiB/s | 6.0–6.2 KiB/s | 21× less |
| Hub CPU, 50 streams | 258–279 % of a core | 110–128 % | 2.3× less |
| SSE cost per user | 4.7–5.2 % of a core | 1.7–2.4 % of a core | 2.5× less |

The remaining per-stream cost is mostly socket writes and flushes and the GC of the 2.2 GiB
heap (see the profile below), not filtering: `flushCounts`, counts included, is 14 % of
the SSE phase.

## Requests under load: budgets

The concurrent phase loads a whole page every think-time per user: `/clusters`, `…/kinds`,
the **full** 15k-row `…/resources` list (12.1 MiB raw, 865 KiB gzipped), fleet and cluster
search, and fleet attention.

### Verdict

- **The SSE goal of P2 is met.** Streams no longer carry every cluster's deltas: 17× fewer
  events, 21× fewer bytes and 2.5× less CPU per user. 50 open streams now cost about one core
  instead of three.
- **Under 50 concurrent users, request latency barely moves.** Live updates were not what
  held it back. Two things cost more:
  1. The load generator still fetches the **whole 15k-row list** on every page view. That is
     about 30 ms to filter plus 30 ms to encode plus 28 ms to gzip, 12 MiB per request, and
     about 25 of them per second at think 2 s. The P2 web half (`view=index`, paging and
     progressive lists) removes this. It is not part of this change.
  2. The fleet-wide search p50 is about 940 ms under load but 35 ms alone. This holds even at
     think 10 s, where the hub uses only 5.4 of 12 cores. That points at contention, not
     saturation. Each fleet search scans up to `GOMAXPROCS` views at once, with no limit
     shared across requests, so a few concurrent searches oversubscribe the CPU. On top of that come GC assists on the
     2.2 GiB heap of `model.Resource` pointers. Bounding search fan-out per request is a
     candidate fix. So is the P3 memory work (T2 off the hub).
- Memory is unchanged at 2.24 GiB of views (1,598 B per row). P2 did not aim to change it.

## Commands

```sh
go run -tags dev ./cmd/eddy-loadgen -clusters 100 -resources 15000 -users 50 -role admin -duration 60s -full-fetch=false -watch -1
go run -tags dev ./cmd/eddy-loadgen -clusters 100 -resources 15000 -users 50 -role admin -duration 60s -full-fetch=false -watch 1
go run -tags dev ./cmd/eddy-loadgen -clusters 100 -resources 15000 -users 50 -role admin -duration 60s -full-fetch=false -watch 1 -think 10s
go run -tags dev ./cmd/eddy-loadgen -clusters 100 -resources 15000 -users 50 -role admin -duration 60s -full-fetch=false -watch 1 -sse-cpuprofile sse.prof
```

`-watch N` makes each user's stream watch N clusters (user i watches clusters i … i+N−1). `0`
sends `watch=` with no value, and `-1` (the default) sends no `watch` and gets the unscoped
stream. The report shows events per second split into `change`, `counts` and `attention`.
These runs used the P2 SSE code on top of `92e1ee5`, without the concurrent
SelfSubjectRulesReview work, and only admin users. Namespace-scoped users are still bound by
the SAR volume that p1.md describes.
